# Categories (per user)

Issue #34. Each user has their own categories. A user has few categories,
so all of them are kept in **one row per user**, as a JSON array, rather
than one row per category.

## Storage

```sql
CREATE TABLE user_categories (
    user_uid   TEXT    PRIMARY KEY REFERENCES users (uid) ON DELETE CASCADE,
    categories TEXT    NOT NULL DEFAULT '[]' CHECK (json_valid(categories) AND json_type(categories) = 'array'),
    version    INTEGER NOT NULL DEFAULT 1 CHECK (version >= 1),
    created_at TEXT    NOT NULL,
    updated_at TEXT
);
CREATE TABLE meta (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL CHECK (json_valid(value)),
    updated_at TEXT NOT NULL
);
```

- `categories` is a JSON array of the same objects the API returns:
  `{"uid","name","type","description","created_at","updated_at"}`.
- The row is created **lazily** on a user's first category write. A user
  without a row simply has no categories.
- Deleting a user deletes the row (`ON DELETE CASCADE`).
- `meta` is a small key/value table for server bookkeeping. A new database
  has no rows in it and no key is currently in use.

Category `uid`s stay **globally unique** UUID v4s generated by the server,
so `transactions.category_uid` still identifies one category (no FK, as
before).

## Rules and limits

The limits are enforced in Go (`pkg/category`, `pkg/store/categories.go`):

| Rule | Value |
|------|-------|
| name | required, ≤ 100 characters (trimmed) |
| description | optional, ≤ 1000 characters |
| type | `expense` or `income` |
| unique name | per user, per type, case-insensitive (Unicode case folding, `strings.EqualFold`; the old table only folded ASCII) → 409 |
| categories per user | at most **500** (`store.MaxCategoriesPerUser`) → 409 |

A full row is therefore at most roughly 0.6 MB, and normally a few kB.

## API

The endpoints and JSON fields are the same as before. Each request works on
the **logged-in user's** categories:

- `GET /api/categories` lists only that user's categories.
- `GET/PUT/DELETE /api/categories/{uid}` returns **404** for a uid that belongs
  to another user (the same as for an unknown uid).
- Deleting a category, or changing its type, returns **409** while any
  transaction references its uid (`transactions.category_uid` is scanned).
- When a transaction is created or updated, its `category_uid` must be one of
  the **current user's** categories with a matching type. Otherwise the
  request fails with 422.

Transactions and balances are **not** per-user yet (follow-up). The in-use
check therefore counts every transaction.

## Concurrency

Every write (create, update, delete) does a read-modify-write of the user's
row inside **one SQL transaction**:

1. Read `categories` and `version`.
2. Apply the change in Go and check uniqueness, limits and in-use rules.
3. Write with `UPDATE ... SET version = version + 1 WHERE user_uid = ? AND
   version = ?`. For a new row it uses `INSERT ... ON CONFLICT DO NOTHING`.

If no row is affected (someone else wrote first), it counts as a conflict.
It also counts as a conflict if SQLite reports `BUSY`/`BUSY_SNAPSHOT`
because another connection or process committed after our read. In both
cases the whole step is **retried once** from a fresh read. If the retry
also conflicts, the store returns an error (500), and nothing is written or
lost. This version is internal. Clients do not send it, and the category
API stays unversioned.

The server uses one SQLite connection, so in-process writes are already
serialized. The version check protects against other processes and against
future changes to the pool size.
